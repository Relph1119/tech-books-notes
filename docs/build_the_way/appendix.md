# 附录 事后诸葛亮会议

现代软件工程的项目回顾模板

## 设想与目标

1. 我们的软件要解决什么问题？是否定义得很清楚？是否对典型用户和典型场景有清晰的描述？
2. 是否有充足的时间来做计划？
3. 团队在计划阶段是如何解决成员对于计划的不同意见？
4. 用户量、用户对重要功能的接受程度和我们事先的预想一致吗？我们离目标更近了吗？
5. 有什么经验教训？如果重来一遍，我们会作如何改进？

## 计划

1. 原计划的工作是否最后都做完了？如果有没做完的，原因何在？
2. 有没有发现做了一些事后看来没必要或没多大价值的事？
3. 每一项任务是否都有定义清晰且可衡量的交付物？
4. 项目的整个过程是否都按照计划进行？
5. 计划中有没有留下缓冲区，缓冲区有作用吗？
6. 将来的计划会做如何调整？（例如修改缓冲区的定义）
7. 我们学到了什么？如果重来一遍，我们会作如何改进？

## 资源

1. 我们有足够的资源来完成各项任务吗？
2. 完成各项任务所需的时间和其他资源是如何估计的，精度如何？
3. 测试的时间、人力及软件、硬件资源是否足够？对于那些不需要编程的资源（美工、设计、文案），是否低估了难度？
4. 是否存在可由他人更高效完成的工作？
5. 有什么经验教训？如果重来一遍，我们会作如何改进？

## 变更管理

1. 所有相关人员都及时收到了变更通知吗？
2. 我们采用了什么标准来决定“推迟”或“必须实现”的变更？
3. 项目的出口条件有清晰的定义吗？
4. 对于可能的变更是否制订了应急计划？
5. 员工是否能够有效地处理意料之外的工作请求？
6. 我们学到了什么？如果重来一遍，我们会作如何改进？

## 设计/实现

1. 设计工作何时由谁完成？是否由合适的时间和人选？
2. 设计过程中有没有碰到摸棱两可的情况，团队是如何解决的？
3. 团队是否运用单元测试、测试驱动开发、UML或其他工具来辅助设计和实现？这些工具有效吗？
4. 哪些功能产生的Bug最多，为什么？发布后又发现了哪些重要的Bug？为什么在设计/开发阶段没有想到这些情况？
5. 代码复审是如何进行的，是否严格执行了代码规范？
6. 我们学到了什么？如果重来一遍，我们会作如何改进？

## 测试/发布

1. 团队是否有测试计划？如果没有，原因何在？
2. 有没有做过正式的验收测试？
3. 团队是否有测试工具来辅助测试？
4. 团队是如何测量并跟踪软件效能的？
5. 从软件实际运行结果来看，这些测试工作有用吗？应作如何改进？
6. 在发布过程中发现了哪些意外问题？
7. 我们学到了什么？如果重来一遍，我们会作如何改进？

## 【总结】
团队的角色，管理与合作

1. 团队的每个角色是如何确定的，是否做到了人尽其才？
2. 团队成员之间有互相帮助过吗？
3. 当出现项目管理或合作方面的问题时，团队成员如何解决？
4. 团队成员明确、公开地表示过对他人帮助的感谢吗？
