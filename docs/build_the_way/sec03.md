## 3.1 实战中的软件工程

MSF（Microsoft Solution Framework）微软解决方案框架：  
1. 推动信息共享与沟通  
2. 学习所有的经验：事后诸葛亮会议  
3. 充分授权和信任  
4. 各司其职，对项目共同负责  
5. 为共同的愿景而工作  
6. 持续交付增量价值  
7. 与顾客合作  
8. 保持敏捷，主动预期并适应变化

## 3.2 需求分析

1. 需求的分类：功能性需求、非功能性需求、对产品开发过程的需求、跨系统的需求
2. Cynefin框架
    - 繁杂（因果关系存在）：感知-分析-响应
    - 复杂（因果关系不明显）：探索-感知-响应
    - 混乱（因果关系很不清晰）：行动-感知-响应
    - 失序（我们不知道自己不知道什么）：了解情况，分类，分而治之
3. 获取用户需求（用户调研）
    - 焦点小组：邀请一群目标用户的代表，加上项目利益相关方，共同讨论用户想要什么、用户对软件的评价等。会有从众心理、对于不熟悉的事物可能无法表达有价值的想法，讨论者容易收到主持人有意或无意的影响。
    - 深入面谈：一对一访谈。
    - 卡片分类：把需求做成规整的小卡片，讨论、明晰定义、归类、排序。
    - 用户调查问卷
    - 用户日志研究
    - 人类学调查
    - 快速原型调研：用纸片快速设计一些界面让用户模拟使用，得到即使反馈。
4. 电梯演说：

::: info 电梯演说模板
我们的产品 **\<名称\>** 是为了解决 **\<目标用户\>** 的痛点，他们需要 **\<Need\>**，但是现有的产品并没有很好地解决这些需求。我们有独特的做法 **\<Approach\>**，能给用户带来好处 **\<Benefit\>**，远远超过竞争对手 **\<Competitor\>**。同时，我们有高效的交付/推广 **\<Delivery\>** 策略，能很快地让目标用户知道我们的产品，实现进一步传播。
:::

    - 成长蓝图：在做具体小事的过程中，积累隐性知识。

## 3.5 软件设计与实现

1. 白板优先：从业务问题出发，用最简单的方框和箭头在白板上勾勒解决方案，用平实的语言和简单的图示撰写设计文档，讨论权衡取舍，在团队内部分享这份简约的文档，收集问题和建议。
2. AI时代下的工程师的不可替代性：
    - 处理遗留系统和复杂系统
    - 掌握默会知识
3. 未来的软件工程师：
    - 系统架构师：定义软件的高层结构与规范；
    - AI协同者：精确地向AI描述需求，并批判性地验证其输出；
    - 问题解决者：专注于创造力、伦理判断、沟通协作等人类独有的价值领域。
4. ”小强地狱机制“：给每个开发者设定一个Bug数量红线，谁超过了，就必须暂停新功能开发，专心致志修复Bug，直至数量降回安全线以下。

## 3.6 软件测试

1. 测试方法：
    - 构建验证测试：冒烟测试
    - 伙伴测试：智能测试平台（精准的变更感知、智能的测试选择、超强的风险预警）
    - 随机探索式测试
    - 混沌工程：定义稳态、建立假设、注入故障、验证假设
2. 常见测试误区：
    - 测试仅需在项目末期实施
    - 测试是机械执行规格说明书的过程
    - 测试代码无须追求高质量
    - AI模型测试等同于准确率优化
3. AI时代的测试工程师的新定位：
    - 从测试执行者变为质量策略师：设计测试策略，指导AI生成有效的测试。
    - 从Bug记录员变为问题诊断专家
    - 从报告编制者变为风险决策者
    - 从文档使用者变为隐性知识挖掘者
4. AI时代的测试工程师的独特价值：
    - 将隐性的业务规则转化为可测试的需求
    - 基于对系统演进历程的立即，预判潜在风险点
    - 设计基于深度业务理解的复杂场景测试
    - 在AI无法理解的业务逻辑灰色地带做出关键判断
5. **测试的终极目的从来不是”证明软件没有Bug“，而是让用户在真实世界里安心使用。**

## 3.7 质量保障

1. 软件工程质量CMMI的5个成熟度等级
    - 一级（初始级）：项目的成功高度依赖个人英雄主义，过程不可预测且难以重复。
    - 二级（管理级）：项目能按计划与流程执行，实现了基本的管理纪律。
    - 三级（明确级）：建立组织级的标准流程，能根据项目特点进行裁剪。
    - 四级（量化管理级）：基于数据对流程和产品进行预测和管理。
    - 五级（优化级）：聚焦于持续的过程改进和创新。
2. QA人员的职责：赋能开发、改进流程、倡导质量文化
3. 团队成员的测试分工：要求新成员在入职时必须修复100个数据问题。原因如下
    - 默会知识的有效传递：要求新人亲手修复数据问题，促使新人建立系统直觉、实现知识深度内化的强制策略。
    - 打破”即插即用“知识误区：只有亲手处理过数据问题的人，才能设计出直击系统本质的测试用例。

## 3.8 稳定、发布和维护

1. 软件发布的最后阶段其实最考验团队的项目管理与决策能力。
2. 每一次正式发布，都会给团队带来短期和长期的成本：
    - 短期成本：发布前的最终测试、提交审核、撰写更新日志等
    - 长期成本：每一个发布到市场的版本，都成为一个需要长期支持和测试的资产。
3. ZBB（零缺陷反弹）的困境抉择：
    - 承认沉没成本，果断放下对过去投入的执念。
    - 基于历史数据进行客观评价，而非依赖乐观的直觉。
    - 依据”项目不可能三角“原则，主动做出取舍。
4. 可控与反馈：
    - 可控：通过技术手段精确控制新功能对用户群体的可见范围。
    - 反馈：从小范围用户（内部员工、早期爱好者）处收集真实的使用数据和问题反馈，作为是否扩大发布范围的决策依据。
