# 第2篇 团队成长与敏捷流程

## 2.1 两人合作

1. 代码复审：捕获“未知的未知”，传递默会知识（如设计权衡的直觉、对代码“坏味道”的敏感度、复杂调试技巧）
2. 代码复审流程：
    - 复审的前置条件：基础质量门禁、自验证、准备变更集。
    - 复审执行：关注AI审查的盲区（设计层面、上下文影响、长期维护、根本原因分析）。
    - 复审决策与技术债务管理：将技术债务显性化。
3. 结对编程：
    - 设计阶段：共同探讨架构的权衡，避免个人思维的局限性。
    - 测试阶段：共同审视和验证棘手的边界条件。
    - 运维阶段：共同确认关键的生产环境变更。
4. 反馈问题：
    - 最外层（行为和结果）：当反馈聚焦于行为和后果时，行为可以改正，后果可以弥补，对方还有挽回局面的机会。
    - 中间层（习惯和动机）：当反馈上升到攻击对方的习惯和动机时，被攻击的一方就比较难表达自身想法并澄清动机。
    - 最内层（本质和固有属性）：当攻击深入到核心时，被攻击一方已然无法回应。
5. 反馈问题的解决方案：
    - 先来一片面包，做好铺垫：强调双方的共同点，从团队共同的愿景讲起，让对方觉得处于一个安全的环境。
    - 然后把肉放上：把建设性的意见技工好，展望将来的成果，强调“过去你做得不够好，但是我们以后可以做得更好”。
    - 再来一片面包，呼应开头：鼓励对方把工作做好。

## 2.2 团队和流程

1. 软件团队模式
    - 主治医师模式：首席程序员负责处理主要模块的设计和编码，其他成员从不同角度支持其工作。
    - 明星模式：主治医师模式运用到极致。
    - 业余剧团模式：每位成员听从中央指挥的统筹安排，每位成员会挑选自己适合的角色。
    - 秘密团队：软件项目在秘密状态下进行，绝对自主，屏蔽噪音，内在驱动，使命凝聚。
    - 特工团队：由具备特殊技能的专业人士组成，负责解决一些棘手且紧迫的问题。
    - 功能团队：由能力不同的成员平等协作，共同完成一个功能。
    - 官僚模式：按照成员的人事关系分层分组来管理。层级越高的领导往往与现实情况脱节的程度越深。
2. 渐进式交付：
    - MVP：最小可行产品，以最快的速度验证产品假设（核心目标），突出核心价值（关键原则）。
    - MBP：最美最全产品，适用于团队对用户需求有深刻洞察且绝对自信的领域。
3. 初学者如何参与开源：
    - 精读项目的邮件列表、核心RFC讨论、关键的合并请求。
    - 修复过时的文档、补充缺失的测试用例、优化持续集成脚本。
    - 将沟通视为一等技能。

## 2.3 敏捷流程

1. 构建团队：以人为本（项目核心是那些有进取心的人）、技术卓越（通过不断提高技术和设计水平，才能获得应对变化的真正能力）、极简主义（最大限度减少不必要的工作量）
2. Scrum敏捷方法论：
    - 找出完成产品需要做的事情：产品待办列表（Product Backlog）
    - 决定当前Sprint需要解决的事情：Sprint Backlog
    - 执行Sprint：每日站会
    - 得到软件的一个增量版本，发布给用户。
3. 敏捷流程对团队的要求：
    - 自主管理：能够自我规划、评估风险并持续改进。
    - 自我组织：形成一种集体所有制的文化，当岗位出现短板时，主动补位。
    - 多功能型：避免出现导致协作阻塞的“知识孤岛”。
4. 开源与敏捷：
    - 从敏捷中学习小步快跑、持续交付、响应变化的价值观。
    - 从开源中学习透明协作、异步沟通、文档驱动、精英治理的协作模式。
